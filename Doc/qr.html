1. Resumen

El QR nativo es el contenido que se codifica dentro del código QR que el cliente escanea para pagar una orden. Se usa en la modalidad Multipago (QR) del medio de pago multipago.

No presenta deuda. El importe y el vencimiento viajan dentro del propio QR, por lo que no se usa la API de obtener_deuda (que reemplazaría toda la base del comercio en Multipago). Multipago lee el monto y la fecha directamente del código escaneado.

La trama es 100% ASCII y se compone de cuatro bloques:

[ cabecera ] [ 81 ][ LL ][ dato ] [ sector2 ] [ CCCC ]
     |              |                 |          |
   convenio     sector1            convenio    CRC16

2. Identificador de cliente

Es la referencia del cliente ante Multipago y es idéntico al del botón de pago (PUM): la parte que identifica al cliente son comercio + id de cliente, sin dígito verificador.

Longitud total
10 dígitos
Comercio
bersacode
Id de cliente
order_id → 6 dígitos
  • Comercio (4 dígitos): el bersacode del convenio, completado con ceros a la izquierda.
  • Id de cliente (6 dígitos): el order_id de la venta; se toman sus últimos large dígitos (parámetro del convenio) y se completa con ceros a la izquierda hasta 6.
identificador = pad4(bersacode) . pad6( substr(order_id, -large) )   // 10 dígitos

ej.:  bersacode = "1234",  order_id = 42,  large = 6
      comercio = "1234"   cliente = "000042"
      identificador = "1234000042"

3. Estructura de la trama

BloqueOrigenDescripción
cabecera header[0 .. -17] Encabezado del convenio sin los últimos 17 caracteres.
81 LL dato sector1 Bloque 81 + largo del dato en 2 dígitos + el dato (TLV).
sector2 header[-17 .. -4] 13 caracteres del encabezado del convenio (entre la cabecera y su CRC de ejemplo).
CCCC crc16 CRC16-CCITT de cabecera + sector1 + sector2.

El header del convenio trae al final 4 caracteres de un CRC de ejemplo que se descarta: se recalcula el CRC real sobre la trama armada.

4. Campos del dato (TLV)

El dato es una sucesión de campos Tag – Length – Value. El largo es de 2 dígitos decimales (con ceros a la izquierda). El orden es fijo:

TagCampoLargoEjemploDescripción
00 Identificador 10 1234000042 Identificador de cliente (comercio + id de cliente).
01 Importe var. 5000.00 Total a pagar, 2 decimales, separador punto (sin separador de miles).
02 Hash corto 4 A32D SHA-256(seeder + identificador), primeros 2 bytes en hex (ver §5).
03 Vencimiento 6 131026 Fecha de vencimiento en ddmmaa (por defecto: ahora + 24 h).
04 Id del pago var. 42 Nuestro order_id. Permite asociar el cobro del webhook a la orden.

Hash corto (tag 02)

hash = SHA-256( seeder . identificador )        // bytes crudos
corto = hex( (byte0 << 8) | byte1 )             // 2 primeros bytes -> 4 hex mayúsculas

Vencimiento (tag 03)

ddmmaa = formato día-mes-año con 2 dígitos cada uno.

6. Ejemplo completo

Con bersacode = 1234, large = 6, order_id = 42, importe = 5000.00, vencimiento = 131026 y header = HDR0000000000000000000SECTOR2AB1234, seeder = semilla-prueba:

identificador
1234000042
hash corto
A32D
cabecera
HDR000000000000000
sector2
0000SECTOR2AB

dato (TLV concatenado):

00 10 1234000042 01 07 5000.00 02 04 A32D 03 06 131026 04 02 42

sector1 = 81 + largo(dato) + dato:

81 49 0010123400004201075000.000204A32D0306131026040242

trama sin CRC = cabecera + sector1 + sector2:

HDR00000000000000081490010123400004201075000.000204A32D03061310260402420000SECTOR2AB

contenido final del QR (trama sin CRC + CCCC):

HDR00000000000000081490010123400004201075000.000204A32D03061310260402420000SECTOR2ABAC82
AC82 es el CRC16-CCITT calculado sobre la trama sin CRC.

7. Webhook de cobro

Multipago notifica el cobro a una única URL (una sola cuenta/URL para toda la instalación), protegida por una webhook_key en la ruta: 

/tickets/multipago/webhook/{webhook_key}

El cuerpo del aviso (JSON) contiene:

{
    "customer_id":   "1234000042",   // identificador (comercio + id de cliente)
    "amount":        5000.00,        // importe cobrado
    "identifier":    "MP-COBRO-1",   // identificador del cobro en Multipago
    "fecha_pago":    "2026-10-13",
    "id_pago":       42              // opcional: nuestro order_id (tag 04)
}

Asociación a la orden

  • Por id_pago: si viene, es directamente nuestro order_id.
  • Por customer_id: si no viene id_pago, se toman los últimos 6 dígitos del identificador (el id de cliente) como order_id.

El cobro se registra y la orden pasa a paid de forma idempotente (se deduplica por identifier).

8. Requisitos de configuración

Para ofrecer la modalidad QR de un evento (o de la cuenta global) hacen falta dos datos que entrega Multipago:

ClaveUso
headerEncabezado del convenio (cabecera + sector2).
seederSemilla del hash corto (tag 02).

Además se usan bersacode (comercio) y large (dígitos de cliente), compartidos con el botón de pago. Sin header y seeder la modalidad QR no se ofrece; con ellos cargados, la generación del QR puede fallar con 422 si se solicita sin la configuración completa.
